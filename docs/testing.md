# Автоматизированное тестирование

## Цель

Настроить воспроизводимое автоматическое тестирование уже реализованного ядра
мониторинга и подготовить отчёты, которые можно расширять вместе с проектом.

## Среда и виды тестирования

- **Go `testing`** — модульные тесты сервисов и контрактов; внешние
  зависимости заменяются тестовыми реализациями или локальными HTTP-серверами.
- **Playwright** — пользовательские сценарии Web UI в Chromium. REST-ответы
  перехватываются в браузере, поэтому тесты не зависят от внешних веб-сервисов.
- **Docker Compose** — интеграционные сценарии инфраструктуры, прототипа и
  ядра мониторинга.
- **GitHub Actions** — единая среда запуска проверок, сборки и публикации
  отчётов.

## Основные сценарии

Модульные тесты проверяют HTTP-проверки (успех, коды ошибок, тайм-аут,
некорректный URL и сетевая ошибка), конфигурацию, REST- и gRPC-обработчики,
состояние версий конфигурации, планирование, запись и чтение InfluxDB.
Дополнительно проверяются ошибки публикации заданий Scheduler Service и
ошибочные gRPC-ответы API Service и Metrics Service.

Playwright проверяет:

1. начальное состояние загрузки;
2. доступный сервис, HTTP-код, время ответа и дату проверки;
3. недоступный сервис и ошибку проверки;
4. обновление результата кнопкой;
5. отсутствие результатов (`404`);
6. ошибку API и отсутствие критической ошибки JavaScript.

## Локальный запуск

В корне репозитория:

```bash
go test ./contracts/... ./services/api/... ./services/checker/... ./services/metrics/... ./services/notification/... ./services/scheduler/...
bash scripts/integration-test.sh
bash scripts/prototype-test.sh
bash scripts/monitoring-core-test.sh
```

Для пользовательских тестов:

```bash
cd web
npm ci
npx playwright install chromium
npm run test:e2e
```

После запуска доступны `web/playwright-report/index.html` и
`web/test-results/junit.xml`. Отчёты создаются заново и не добавляются в Git.

## GitHub Actions и отчёты

CI запускает проверку сообщений коммитов, форматирование и статический анализ
Go, Go-тесты, ESLint, сборку Web UI, Playwright и три Docker-интеграции.

В Job Summary публикуются количество успешных и неуспешных Go- и
Playwright-тестов, а также существующая сводка метрик качества. В Artifacts
доступны:

- `go-coverage` — профили покрытия Go;
- `go-test-reports` — JSON результатов Go-тестов и их профили покрытия;
- `playwright-report` — HTML-отчёт, JUnit XML и trace при сбое;
- `application-build` — собранное приложение;
- `quality-metrics` — JSON метрик и агрегированные результаты Go-тестов.

Артефакты загрузки используют `if: always()`, поэтому результаты уже
запущенных тестов сохраняются и при ошибке последующей проверки.

## Метрики и ограничения

Исторические измерения по этапам хранятся отдельно в
[`metrics/stages.md`](../metrics/stages.md). Актуальные количество тестов,
покрытие, сложность и длительность CI рассчитываются автоматически в каждом
запуске GitHub Actions и доступны в Job Summary и артефакте
`quality-metrics`.

Известное замечание по сторонней зависимости зафиксировано в
[аудите зависимостей](dependency-audit.md).

Покрытие не стремится к 100%: точки входа процессов, подключения к реальным
PostgreSQL/RabbitMQ/InfluxDB и будущий Notification Service проверяются
интеграционно либо ещё не содержат завершённой бизнес-логики. Для будущих
функций из матрицы нужно добавлять тесты одновременно с их реализацией.
